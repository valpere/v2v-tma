# v2v-tma — Requirements Specification

Документ визначає функціональні (FR), нефункціональні (NFR) та інтерфейсні вимоги до системи.

---

## 1. Функціональні вимоги (Functional Requirements)

### FR-1: Безпека та автентифікація Telegram
- **FR-1.1:** Система повинна перевіряти підпис `initData` на бекенді за стандартом Telegram: HMAC-SHA256 хеш від відсортованих параметрів із використанням SHA256(`bot_token`) як секретного ключа.
- **FR-1.2:** Токени або сесії повинні мати обмежений термін життя (TTL не більше 24 годин).
- **FR-1.3:** Невалідовані запити повинні блокуватися зі статусом `401 Unauthorized` або перенаправлятися в ізольований read-only демо-режим.

### FR-2: Мультидоменна база знань (Multi-Domain KB)
- **FR-2.1:** Система повинна підтримувати ізольовані домени (як мінімум 4 за замовчуванням: Pizzeria, Barbershop, Auto Service, Health Shop).
- **FR-2.2:** Кожен домен повинен містити:
  - Каталог товарів/послуг (ідентифікатор, назва, опис, ціна в UAH, еквівалент у Stars, іконка/зображення).
  - Правила та контекст бізнесу (години роботи, умови доставки/запису, політика скасування).
- **FR-2.3:** Перемикання домену в UI повинно відбуватися клієнтсько без перезавантаження сторінки з синхронізацією стану на сервері.

### FR-3: Діалогова логіка та генерація UI-дій (Structured LLM Actions)
- **FR-3.1:** Відповідь LLM повинна бути строго структурованою у форматі JSON з такими обов'язковими полями:
  - `reply_text` (текстове повідомлення користувачеві).
  - `language` (`uk` або `en`).
  - `ui_actions` (масив дій: `highlight_item`, `add_to_cart`, `remove_from_cart`, `set_domain`, `open_checkout`).
  - `intent` (ідентифікатор наміру: `order`, `query_price`, `booking`, `out_of_scope`).
- **FR-3.2:** LLM повинна бути заземлена строго на KB обраного домену з забороною вигадування товарів чи цін.

### FR-4: Подвійний режим роботи: Текст (Zero-Cost) та Голос (On-Demand)
- **FR-4.1:** **Режим за замовчуванням — Текстовий.** Жодні виклики до платних сервісів TTS/STT не відбуваються, поки користувач явно не активує голос.
- **FR-4.2:** Система повинна підтримувати локальний Web Speech API браузера для синтезу/розпізнавання без звернення до хмарних провайдерів (нульова собівартість).
- **FR-4.3:** При активації хмарного режиму голосу (On-Demand Cloud TTS/STT) система повинна підтримувати кешування аудіо за хешем репліки, щоб повторні типові відповіді не синтезувалися двічі.

### FR-5: Інтеграція платежів Telegram Stars
- **FR-5.1:** Система повинна інтегруватися з офіційним Telegram Payments API через бот-токен:
  - Генерація платіжного посилання через метод `createInvoiceLink` із валютою `XTR` (Telegram Stars).
  - Відкриття інвойсу у клієнті через метод SDK `Telegram.WebApp.openInvoice(url, callback)`.
- **FR-5.2:** Бекенд повинен обробляти `pre_checkout_query` від Telegram, підтверджуючи платіж протягом 10 секунд.
- **FR-5.3:** Після підтвердження платежу транзакція фіксується як сплачена з відправкою чека користувачеві у приватний чат.

## 2. Нефункціональні вимоги (Non-Functional Requirements)

### NFR-1: Швидкодія та затримки (Performance & Latency)
- **NFR-1.1:** Первинне завантаження Mini App (FCP — First Contentful Paint) на мобільному 4G зв'язку має тривати **менше 1.2 секунди**.
- **NFR-1.2:** Загальна вага клієнтського бандлу (HTML + CSS + JS) не повинна перевищувати **150 KB** (без важких фреймворків).
- **NFR-1.3:** Час відповіді сервера на текстовий запит (LLM generation + UI action parsing) — **до 1.5 секунди**.
- **NFR-1.4:** Затримка голосового відтворення (Push-to-Talk → розпізнавання → відповідь) — **до 2.5 секунди** (хмарний режим) або **до 800 мс** (локальний клієнтський режим).

### NFR-2: Нативність та мобільний UX (Mobile-First TMA Experience)
- **NFR-2.1:** Застосунок повинен повністю підтримувати системні кольори Telegram (`themeParams.bg_color`, `themeParams.text_color` тощо).
- **NFR-2.2:** Усі ключові дії користувача (додавання в кошик, відкриття шторки, оплата) повинні супроводжуватися відповідним тактильним відгуком через `Telegram.WebApp.HapticFeedback` (`impactOccurred('medium')`, `notificationOccurred('success')`).
- **NFR-2.3:** Застосунок повинен коректно розгортатися на повний екран (`Telegram.WebApp.expand()`) без появи небажаних скролбарів та зміщень форми при відкритті віртуальної клавіатури на iOS та Android.

### NFR-3: Стійкість та відмовостійкість (Reliability)
- **NFR-3.1:** При відсутності зв'язку з хмарними STT/TTS сервісами система повинна автоматично деградувати до текстового режиму або браузерного Web Speech API без падіння інтерфейсу.
- **NFR-3.2:** Усі платіжні операції повинні бути ідемпотентними: повторний виклик або дублювання webhook-повідомлення не повинні призводити до повторного нарахування товарів чи списання зірок.
